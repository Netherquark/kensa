\section{Problem Statement}

The 40 MHz benchmark represents reconstructed trigger-level objects from simulated proton-proton collisions. Its tensor layout is compact at the file level, while the raw numerical array has a substantially larger uncompressed representation. Reliable analysis requires explicit handling of tensor dimensions, data types, structural padding, and event-level feature definitions before SQL or machine-learning operations begin.

The research question is: \emph{Can a reproducible, bounded-memory pipeline validate every event in the published training file, transform its object tensor into an auditable analytical table, and use Big Data operations to describe event kinematics and rank unusual feature combinations on a six-core Linux host?}

The dataset file \texttt{background\_for\_training.h5} ($646.4\,\text{MB}$, MD5 \texttt{08cb4801229f9d480567f8d3f5cac134}) from Zenodo Record 5046428 contains 4,000,000 collision events according to the dataset paper~\cite{govorkova2022lhc}. Each event is a $(19 \times 4)$ floating-point tensor with 304,000,000 total scalar fields.

\textbf{Scope Boundaries:} Spark runs in \texttt{local[6]} mode inside one Docker host. This configuration exercises parallel tasks and shuffle behaviour within one machine. It does not measure multi-node speed-up or Level-1 trigger latency. The primary training record supplies no per-event label identifying a hidden new-physics signal; the project therefore does not calculate supervised classification accuracy, ROC-AUC, signal efficiency, precision, recall, or discovery significance from this file alone.

\section{Background and Physics Context}

\subsection{Trigger-level data analytics}

At the Large Hadron Collider, proton bunch crossings occur at a nominal frequency of \(40\,\mathrm{MHz}\), corresponding to \(25\,\mathrm{ns}\) between crossings. Online trigger systems reduce the event rate before permanent storage. Their algorithms use reconstructed objects such as electrons, muons, jets, and missing transverse momentum. The open benchmark supports research on anomaly-detection methods operating in a trigger-level setting~\cite{govorkova2022lhc,zenodo5046428,adc2021}.

The data product analysed here is an offline file released for research. Wall-clock timings produced by this project describe file processing on the chosen host. They do not establish that a model could make a trigger decision within a hardware latency budget.

\subsection{Simulation and event selection}

The dataset paper documents simulated proton-proton collisions at a centre-of-mass energy of \(13\,\mathrm{TeV}\), generated with PYTHIA and passed through a parametric detector simulation based on DELPHES. The training sample uses a single-lepton trigger selection. The published selection requires an electron or muon above a transverse-momentum threshold, with species-dependent pseudorapidity acceptance. Reconstructed objects are represented by a bounded number of slots per event~\cite{govorkova2022lhc}.

Observed distributions reflect the generator configuration, detector simulation, object reconstruction, and event selection. They are not an unbiased census of every physical collision at the LHC.

The background training corpus represents a physics cocktail of four dominant Standard Model processes produced in high-energy $pp$ collisions~\cite{govorkova2022lhc}:

The fourth tensor component encodes reconstructed object type; it does not encode the underlying event's generator process. The integer type codes stored in the dataset indicate reconstructed particle species (MET, electron, muon, jet, padding), not generator process classes. No per-event process truth is available in the training corpus.

\subsection{Physics terms required to read the analysis}

A collision event is represented by reconstructed physics objects. An object slot stores transverse momentum \(\pt\), pseudorapidity \(\eta\), azimuth \(\phi\), and a categorical type code. Transverse momentum is the magnitude of momentum projected onto the plane perpendicular to the beam axis. For Cartesian components \(p_x,p_y\),
\begin{equation}\pt=\sqrt{p_x^2+p_y^2}.\label{eq:pt}\end{equation}
In the dataset convention, transverse momentum is expressed in GeV under natural units with \(c=1\).

Pseudorapidity is defined from polar angle \(\theta\), measured relative to the beam direction:
\begin{equation}\eta=-\ln\left[\tan\left(\frac{\theta}{2}\right)\right].\label{eq:eta}\end{equation}
For highly relativistic particles, pseudorapidity approximates rapidity, ensuring differences \(\Delta\eta\) are invariant under longitudinal Lorentz boosts.

The variable provides a convenient angular coordinate for collider detectors. Azimuth \(\phi\) specifies orientation in the transverse plane and is periodic over an interval represented as \([-\pi,\pi]\). An angular difference must respect this periodic boundary:
\begin{equation}\Delta\phi(a,b)=\operatorname{atan2}\bigl(\sin(\phi_a-\phi_b),\cos(\phi_a-\phi_b)\bigr).\label{eq:dphi}\end{equation}
The current feature table retains the stored MET azimuth but does not implement pairwise angular separation as a derived feature.

Missing transverse momentum is a vector quantity representing transverse momentum imbalance. The table uses the magnitude stored in the designated MET slot. The pipeline does not reconstruct the vector from the other slots, so interpretations remain tied to the published object representation.

Jet multiplicity \(\njet\) counts reconstructed jet slots. Scalar jet activity \(\HT\) sums jet transverse-momentum magnitudes. Scalar lepton activity \(\STlep\) sums electron and muon transverse-momentum magnitudes. These scalar quantities describe event activity and support stratified summaries. They are not invariant-mass observables.

\subsection{Fixed-Width Tensor Layout and Padding Semantics}

Each event is a fixed $(19 \times 4)$ tensor. The 19 slots are allocated into four object segments:
\begin{equation}
    \text{Slot Layout: } \underbrace{\text{Slot } 0}_{\text{MET } (t=1)} \quad \underbrace{\text{Slots } 1\dots 4}_{\text{Electrons } (t=2)} \quad \underbrace{\text{Slots } 5\dots 8}_{\text{Muons } (t=3)} \quad \underbrace{\text{Slots } 9\dots 18}_{\text{Jets } (t=4)}.
\end{equation}
Within each group, objects are sorted in descending transverse momentum. Unused slots have type code $t_i = 0$ and all kinematic fields set to $0.0$.

Type code $0$ denotes structural padding required by the tensor shape. It is not missing data or a corrupt reading. The ETL pipeline distinguishes valid padding from corruption by checking that padding slots have all zero kinematic fields:
\begin{equation}
    (t_i = 0) \implies (p_{T,i} = 0.0 \land \phi_i = 0.0 \land \eta_i = 0.0).
\end{equation}

\subsection{Unsupervised anomaly scoring rationale}

Searching for unexpected new physics without specific model assumptions requires unsupervised anomaly detection. Anomalous events are rare and unpredictable, so supervised classifiers cannot be trained against known signal topologies.

This study implements an unsupervised clustering model (\texttt{MiniBatchKMeans}, $K=8$) operating on standardized kinematic features $\mathbf{z} \in \mathbb{R}^{10}$. The atypicality score $s(\mathbf{x})$ of an event $\mathbf{x}$ is the minimum Euclidean distance in standardized feature space to the nearest cluster centroid $\boldsymbol{\mu}_k$:
\begin{equation}
    s(\mathbf{x}) = \min_{k} \|\mathbf{z}(\mathbf{x}) - \boldsymbol{\mu}_k\|_2.
\end{equation}
This distance measures geometric eccentricity relative to typical Standard Model distributions. Events with large $s(\mathbf{x})$ reside in sparse topological regions. The score is an exploratory distance metric, not a calibrated probability of new physics~\cite{adc2021}.

The final tensor component carries the categorical code. Because HDF5 may store the complete tensor in a floating-point dtype, the implementation checks that each finite type value lies within tolerance of an integer and belongs to \(\{0,1,2,3,4\}\) before casting. A direct integer cast without this check could silently map malformed values onto valid category codes.

For the published shape \((4{,}000{,}000,19,4)\), the tensor contains
\begin{equation}4{,}000{,}000\times19\times4=304{,}000{,}000\label{eq:scalarcount}\end{equation}
scalar entries. For a verified \texttt{float64} dtype, the uncompressed numeric payload is \(304{,}000{,}000\times8=2.432\times10^9\) bytes, before HDF5 chunk metadata and compression. This calculation follows from published cardinality; the audit records the observed runtime shape and dtype.

\subsection{Structural padding and data quality}

Each event has fixed slot capacity. A zero type code denotes padding when all three kinematic coordinates in that slot are also zero. Padding is an expected representation detail. It must be counted separately from invalid numeric values, invalid type codes, and negative transverse momentum in occupied slots.

The audit implements these checks:
\begin{itemize}
  \item finite scalar check for every tensor value, with separate NaN and positive/negative infinity counts;
  \item categorical type-code check, including non-integral values and unknown codes;
  \item expected slot-position check for occupied MET, electron, muon, and jet objects;
  \item negative \(\pt\) count among occupied objects;
  \item azimuth-boundary count for occupied objects under a documented numerical tolerance;
  \item padding-consistency check for empty slots containing nonzero kinematic values;
  \item slot-occupancy and per-event multiplicity distributions.
\end{itemize}

Execution results are generated from the actual audit manifest. Zero defect counts are conclusions only after the complete file has been scanned successfully.

\subsection{Limitations of the record}

The main file is simulated and selected. It has no documented event-level truth field for the hidden black-box signal. Object type codes identify reconstructed object categories. The training file cannot establish signal discrimination quality in isolation. Detector response, generator configuration, trigger selection, pile-up settings, and fixed object limits shape feature distributions and must remain part of interpretation.

\section{Methodology}

\subsection{Execution contract}

The pipeline enforces four invariants. First, download is accepted only after matching the repository-listed checksum and API byte count. Second, HDF5 schema validation occurs before feature extraction. Third, each source row produces exactly one output event row. Fourth, Parquet, Spark, and MapReduce event totals must agree. A stage that violates its invariant terminates with an error.

All raw-data reads use fixed-size chunks. The default chunk length is 25,000 event rows. With 19 slots and four scalar values per slot, each input chunk has at most \(25{,}000\times19\times4\) values. Temporary NumPy arrays and validity masks increase memory use beyond the source array alone; the batch size is configurable.

\subsection{Pipeline stages}

The pipeline executes six sequential stages, each gated on the prior stage's validated output:

\begin{enumerate}
  \item \textbf{Fetch and verify.} Query Zenodo metadata, locate the intended file, download to a temporary file, calculate MD5, check byte count, and move the file into the raw-data directory only after successful verification.
  \item \textbf{Inspect and audit.} Enumerate HDF5 datasets, shapes, dtypes, compression, chunk geometry, attributes and small metadata values. Scan every \texttt{/Particles} chunk and accumulate quality counters and full-corpus histograms.
  \item \textbf{Derive event variables.} For every chunk, form slot masks from validated type codes, calculate object counts and scalar activities, retain a zero-based source row ordinal, and save event-level defect flags.
  \item \textbf{Write Parquet.} Append typed Arrow tables to a Snappy-compressed Parquet file. Record row count, row-group count, file size, column types and feature definitions. Reopen the output and verify its row count.
  \item \textbf{Run Spark analyses.} Read the complete Parquet table, repartition it by jet multiplicity, write a partitioned Parquet copy, read it back, and compare event totals. Execute seven SQL scripts and preserve outputs plus a manifest.
  \item \textbf{Aggregate with RDDs.} Map each event to key \(\njet\) and a tuple of count and feature sums. Reduce tuples by key, calculate means, and check that grouped counts sum to the input event count.
  \item \textbf{Visualize.} Build figures from exact audit histograms, complete event-level features, query results and optional clustering scores. Every visual records its data basis in a JSON manifest.
  \item \textbf{Optional outlier ranking.} Stream feature batches through standardization, cluster fitting, and scoring. Verify that the scored row count equals the Parquet row count.
\end{enumerate}

\section{Implementation, Queries, and Algorithms}

\subsection{Feature engineering}

Define the indicator for particle category \(c\) as
\begin{equation}I_{ei}^{(c)}=\mathbf{1}[t_{ei}=c].\end{equation}
Electron, muon and jet counts for event \(e\) are
\begin{align}
N_e(e)&=\sum_{i=0}^{18}I_{ei}^{(2)}, & N_\mu(e)&=\sum_{i=0}^{18}I_{ei}^{(3)},\\
\njet(e)&=\sum_{i=0}^{18}I_{ei}^{(4)}, & N_{\mathrm{objects}}(e)&=N_e(e)+N_\mu(e)+\njet(e).
\end{align}
The MET object is stored in slot 0. Scalar activity variables are
\begin{align}
\HT(e)&=\sum_{i=0}^{18}p_{\mathrm{T},ei}I_{ei}^{(4)},\\
\STlep(e)&=\sum_{i=0}^{18}p_{\mathrm{T},ei}\left(I_{ei}^{(2)}+I_{ei}^{(3)}\right).
\end{align}
For object category \(c\), leading transverse momentum is
\begin{equation}
\pt^{\mathrm{lead},c}(e)=\begin{cases}\max\{p_{\mathrm{T},ei}:t_{ei}=c\},&\text{if category }c\text{ is present},\\0,&\text{if category }c\text{ is absent}.\end{cases}
\end{equation}
The implementation also stores maximum absolute pseudorapidity across electrons, muons and jets, plus event-level quality counters. When no valid object of a category exists, its leading-object value is zero by definition; this convention affects interpretation of low-value bins.

The projected Parquet schema has 17 columns: source row ordinal; MET magnitude and azimuth; electron, muon, jet and total-object counts; leading \(\pt\) for three species; \(\HT\); \(\STlep\); maximum absolute pseudorapidity; a non-finite flag; invalid-type count; negative-\(\pt\) count; and inconsistent-padding count. The ETL manifest stores detailed definitions and Arrow types.

\subsection{Parquet contract}

Parquet stores values by column within row groups. Snappy compression reduces on-disk volume and allows Spark to request selected columns. HDF5 chunks and Parquet row groups are connected through a bounded-memory writer. The manifest reports actual output size and row-group count. For a four-million-row input and a 25,000-row batch, the expected number of input chunks is 160. Actual row groups must be read from file metadata because writer behaviour and configuration determine the exact count.

The ETL assertions are
\begin{equation}N_{\mathrm{HDF5\ rows\ read}}=N_{\mathrm{Parquet\ rows\ written}},\qquad N_{\mathrm{filtered}}=N_{\mathrm{sampled}}=0.\end{equation}
A stable \texttt{event\_row\_id} retains the zero-based source ordinal; it is not a physical event identifier.

\subsection{MapReduce key-value aggregation}

For each event row, the mapper emits
\begin{equation}\left(\njet,\ (1,\HT,\met,\STlep)\right).\end{equation}
The value contains an event count and three additive statistics. For fixed key \(j\), the reducer applies componentwise addition:
\begin{equation}
(n,s_H,s_M,s_L)\oplus(n',s'_H,s'_M,s'_L)=(n+n',s_H+s'_H,s_M+s'_M,s_L+s'_L).
\end{equation}
The final means are \(s_H/n\), \(s_M/n\), and \(s_L/n\). Componentwise addition is associative and commutative, so partial aggregates can be combined before the final reduction. The acceptance condition is
\begin{equation}\sum_j n_j=N_{\mathrm{input\ events}}.\end{equation}

The Spark RDD implementation executes this calculation in the default runtime. Separate mapper and reducer scripts implement the Hadoop Streaming text protocol. A Hadoop Streaming run requires an external Hadoop installation and a compatible input filesystem; the scripts alone do not prove that such a job has run.

\subsection{Hive and Pig integration}

The Hive DDL defines an external, partitioned table over the Parquet directory written by Spark. External-table registration exposes existing files to Hive's catalog and separates table metadata from file management. The script must be executed by a configured Hive service with the correct filesystem path and warehouse settings. Spark SQL execution does not provide evidence of a HiveServer2 query run.

The Pig Latin script reads a five-column TSV projection containing event ordinal, jet multiplicity, MET, \(\HT\), and \(\STlep\). It groups rows by \(\njet\), calculates count and mean values with \texttt{COUNT} and \texttt{AVG}, sorts by key, and stores the summary. The optional Docker image uses Pig local mode. It is a grouped-dataflow demonstration; no multi-node Pig execution is claimed.

\subsection{Optional MiniBatchKMeans ranking}

The optional model uses ten numeric features: MET magnitude, \(\HT\), \(\STlep\), three multiplicities, three leading-object transverse momenta, and maximum absolute pseudorapidity. A three-pass routine bounds memory.

First, \texttt{StandardScaler.partial\_fit} accumulates feature means and scales across every batch. For feature \(j\), the standardized value is
\begin{equation}z_j=\frac{x_j-\mu_j}{\sigma_j},\end{equation}
where \(\mu_j\) and \(\sigma_j\) are estimated from the complete input. Zero-variance handling follows scikit-learn's scaler implementation.

Second, \texttt{MiniBatchKMeans.partial\_fit} updates \(K=8\) centroids from batches of standardized observations. The run fixes random state 27 and derives batch size from the configured row batch. Third, each row receives its assigned centroid and distance to the nearest centroid:
\begin{equation}s(\mathbf{x})=\min_{1\leq k\leq K}\|\mathbf{z}(\mathbf{x})-\boldsymbol{\mu}_k\|_2.\label{eq:score}\end{equation}
This is Euclidean distance in standardized feature space. It is not a Mahalanobis distance and it is not a calibrated probability. The batch-based optimization, finite training mixture, feature scaling, and lack of per-event signal truth limit its scientific meaning. An upper-tail score identifies candidates for review. It does not establish a new particle or a discovery. The implementation follows scikit-learn's API documentation.

\subsection{Interpretation rules}

The report interprets outputs under four evidence classes:
\begin{itemize}
  \item \textbf{Published fact}: a dataset property or process proportion documented by the research article or repository.
  \item \textbf{Calculated quantity}: an arithmetic consequence of a verified shape, dtype, or output table.
  \item \textbf{Local measurement}: a count, mean, or histogram derived from the actual downloaded file and recorded in a JSON manifest.
  \item \textbf{Conditional variable}: a figure or table that appears only when its generating script has produced a matching artifact.
\end{itemize}
The report does not mix these classes. When a local measurement is absent, the corresponding section states that the value must be read from the generated manifest in lieu of typing missing values.

\section{Mathematical Algorithms and Query Logic}

\subsection{Feature Engineering Mathematical Definitions}

Let $i \in \{0, 1, \dots, 18\}$ index the 19 particle slots for event $e$, with transverse momentum $p_{T, i}$, pseudorapidity $\eta_i$, azimuth $\phi_i$, and type code $t_i \in \{0, 1, 2, 3, 4\}$.
\begin{equation}
N_e = \sum_{i=0}^{18} \mathbf{1}(t_i = 2), \quad
N_\mu = \sum_{i=0}^{18} \mathbf{1}(t_i = 3), \quad
N_j = \sum_{i=0}^{18} \mathbf{1}(t_i = 4)
\end{equation}
\begin{equation}
H_T^{\text{jets}} = \sum_{i=0}^{18} p_{T, i} \cdot \mathbf{1}(t_i = 4), \qquad
S_T^{\text{leptons}} = \sum_{i=0}^{18} p_{T, i} \cdot \mathbf{1}(t_i \in \{2, 3\})
\end{equation}
\begin{equation}
p_T^{\text{lead}, e} = \max_{i: t_i=2} (p_{T, i}), \quad
p_T^{\text{lead}, j} = \max_{i: t_i=4} (p_{T, i}), \quad
|\eta|_{\max} = \max_{i: t_i \in \{2, 3, 4\}} |\eta_i|
\end{equation}

\subsection{MapReduce Distributed Key-Value Formulation}

The mapper transforms each event row into key-value pairs keyed by jet multiplicity $N_{\text{jets}}$:
\begin{equation}
\text{Map}(e) \mapsto \left( N_{j, e}, \; \left( 1, \; H_{T, e}^{\text{jets}}, \; \text{MET}_e, \; S_{T, e}^{\text{leptons}} \right) \right)
\end{equation}
The reducer executes associative and commutative elementwise addition over all partition records:
\begin{equation}
\text{Reduce}(k, [v_1, v_2, \dots]) \mapsto \left( \sum 1, \; \sum H_T^{\text{jets}}, \; \sum \text{MET}, \; \sum S_T^{\text{leptons}} \right)
\end{equation}

\section{Conclusion}

This case study defines a reproducible analysis of the main LHC 40 MHz Standard Model training file. Its technical contribution is an auditable progression from a verified hierarchical tensor to a typed event table, SQL summaries, key-value aggregates and interpretable plots. Quality counters remain attached to derived rows so downstream analysis can account for source integrity.

The project maps to BDA concepts in chunked ingestion, data validation, columnar storage, SQL group operations, partitioned datasets, key-value reduction and visual analytics. Hadoop Streaming, Hive DDL and Pig Latin provide separate ecosystem artefacts whose runtime conditions are stated. Their presence must be paired with successful execution logs before claiming native Hadoop, Hive or distributed Pig operation. The optional clustering component uses scikit-learn; an Apache Mahout implementation is outside the current codebase.

The published record contains four million Standard Model training events. Final numerical results must be drawn from the checksum-verified local run. A previous report draft contained a conflicting row count and dependent figures; those values are excluded until the actual HDF5 shape and all dependent outputs have been regenerated. The training record alone does not justify an event-level new-physics claim.
